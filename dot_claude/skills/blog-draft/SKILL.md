# Blog Draft スキル

白紙から書かせない。本人がやるのは「選ぶ・答える・磨く」だけにして、残りを引き受ける。

## 設定

- **Vaultパス**: `/Users/hakshu/Library/Mobile Documents/iCloud~md~obsidian/Documents`
- **ネタ帳**: `{VAULT}/ブログ/ネタ帳.md`
- **下書きフォルダ**: `{VAULT}/ブログ/drafts/`
- **ブログリポジトリ**: `~/workspace/hakshu.blog`
- **記事の置き場**: `~/workspace/hakshu.blog/content/articles/{slug}.md`
- **文体ガイド**: このスキルの `references/style-guide.md`（初稿を書く前に必ず読む）

## 状態管理

下書きの frontmatter の `status` で進行状況を持つ。`daily-planning` もこれを読む。

| status | 意味 | 次の一手 |
|---|---|---|
| `outline` | 骨子ができ、質問を投げた | 本人が質問に答える |
| `draft` | 初稿ができた | 本人が30分推敲する |
| `review` | 推敲が済んだ | 入稿する |
| `published` | リポジトリに入稿済み | — |

**仕掛かりは常に1本まで。** `published` 以外の下書きがあるときは新しい記事を始めず、その続きから再開する。本人が明示的に「別のを書く」と言ったときだけ例外にする。

## 実行フロー

### ステップ0: 再開か新規かを決める

```bash
VAULT="/Users/hakshu/Library/Mobile Documents/iCloud~md~obsidian/Documents"
grep -L "^status: published" "$VAULT/ブログ/drafts/"*.md 2>/dev/null
```

仕掛かりがあればその `status` に対応するステップへ飛ぶ。なければステップ1へ。

### ステップ1: ネタを選ぶ

本人がネタを指定していればそれを使う。指定がなければ `ネタ帳.md` の未チェック候補を見せて選んでもらう。ネタ帳が空なら先に `blog-ideas` を実行する。

選ばれた候補はネタ帳で `- [x]` にする。

### ステップ2: 骨子を作る

1. 候補の「元ノート」を全部読む。
2. `references/style-guide.md` を読み、記事タイプに合う構成を選ぶ。
3. 見出し構成と、各見出しで書くことを1〜2行ずつまとめる。
4. slug を決める（英小文字とハイフン。例: `vite-plus-build-config`）。
5. 下書きファイル `{VAULT}/ブログ/drafts/{slug}.md` を作る。

```markdown
---
title: （仮）Vite+ に移行してビルド構成がどう変わったか
status: outline
slug: vite-plus-build-config
type: 移行記
source:
  - "[[vite-plus ビルド構成調査]]"
created: 2026-09-21
---

## 骨子

### はじめに
- 何に困っていたか、なぜ移行しようと思ったか

### （見出し）
- ...

## 質問

1. ...

## 回答

```

### ステップ3: インタビューする

元ノートからは分からない、**本人にしか書けないこと**を3〜5問だけ聞く。ネタ帳の「足りないもの」があればそこから作る。

質問の型：

- きっかけ: 「なんでこれを調べよう／やろうと思ったの？」
- ハマり: 「いちばん時間を溶かしたのはどこ？ どうやって原因に気づいた？」
- 判断: 「AじゃなくてBにしたのはなぜ？ 見送ったことはある？」
- 数字: 「どのくらいかかった？ 前後で何がどれだけ変わった？」
- 感想: 「やってみて意外だったことは？ 次にやるなら何を変える？」

伝え方：

- 質問はまとめて番号付きで出す。
- 「箇条書きでも雑でも音声入力でもいい。1問1〜3行で十分」と添えて、答えるハードルを下げる。
- 答えたくない質問は飛ばしていいと伝える。

回答をもらったら下書きの「回答」に**本人の言葉のまま**記録し、次へ進む。その場で答えが出ないときは `status: outline` のまま終了し、次の一手が「質問に答える」であることを伝える。

### ステップ4: 初稿を書く

1. `references/style-guide.md` をもう一度確認する。
2. 骨子・元ノート・回答から本文を書く。回答の言い回しはできるだけそのまま活かす。
3. 聞いていない経験や感想を作らない。埋められない箇所は `<!-- TODO: 〜 -->` で穴を残す。
4. 下書きファイルの「骨子」「質問」「回答」の下に `## 本文` として書き、`status: draft` にする。
5. title と excerpt（100字前後）の案を frontmatter に入れる。

書き終えたら、次の推敲でやることを伝える：

> 推敲は30分で打ち切り。やるのは3つだけ。
> 1. 「はじめに」と「まとめ」を自分の言葉で書き直す
> 2. TODO コメントを埋めるか消す
> 3. 事実（バージョン、数字、リンク）を確かめる

### ステップ5: 推敲を手伝う（頼まれたときだけ）

本人が手を入れた後に頼まれたら、次だけを見る。勝手に全面的な書き直しはしない。

- 事実の誤り・リンク切れ・バージョン表記
- 文体ガイドの「避けること」に当たる表現
- 説明の飛び（前提なしに出てくる用語）

推敲が済んだら `status: review` にする。

### ステップ6: 入稿する

1. 下書きの `## 本文` 以下を取り出し、`~/workspace/hakshu.blog/content/articles/{slug}.md` に書く。
2. frontmatter はブログのスキーマに合わせる。`app/content/schema.ts` の Zod スキーマにより **title / excerpt / readTime / image は文字列、date は `YYYY-MM-DD` 形式の文字列、tags は文字列配列が必須**。欠けたり形が違ったりするとビルドが落ちる。

```markdown
---
title: Vite+ に移行してビルド構成がどう変わったか
excerpt: （100字前後の要約）
date: '2026-09-21'
readTime: 8分
tags:
  - Vite
  - フロントエンド
image: ''
---
```

- `date` は既存記事と同じく引用符付きの `'YYYY-MM-DD'`。引用符がないと YAML パーサによっては日付型として読まれ、文字列チェックに落ちる。
- `readTime` は本文の文字数 ÷ 500 を切り上げて「N分」。
- `tags` は2〜4個。既存記事のタグと表記を揃える。
- `image` は使う画像がなければ空文字列 `''`。
- 公開前の記事を置いておくときは `draft: true` を付ける。一覧・記事ページ・RSS のどれにも出なくなる。
- 本文は MDX（`.md` モード）で変換される。生の HTML タグは描画されないので、Markdown の記法で書く。
- `status`／`slug`／`type`／`source`／`created` はブログ側に持ち込まない。
- Obsidian の `[[wikilink]]` が本文に残っていたら通常のリンクか地の文に直す。

3. リポジトリでビルドして frontmatter の検証を通す（`content/articles/**/*.md` は `vp fmt` の対象外なので、記事の検証はビルドで行う）。ビルドすると全ページが `build/client` に prerender される。見た目を確かめたいときは `vp run preview` で http://localhost:4173 を開く。

```bash
cd ~/workspace/hakshu.blog
vp run build
```

4. 下書きを `status: published` にする。
5. **コミット・push・PR 作成はしない。** 変更したファイルを伝えて終わる。本人が自分でやる。頼まれたときだけ、conventional commits（例: `feat: add article about vite-plus build config`）でコミットする。

---

## 注意

- `content/articles/` にある 2026-01 付近の6本（React 19、AWS Lambda など）はテーマ確認用のダミー記事。文体の参考にしない。
- 1記事1発見。骨子の段階で見出しが6つを超えたら分割を提案する。
- 記事の分量は文体ガイドの目安に従う。長くして埋めない。
